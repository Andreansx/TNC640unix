0. CORRECTION TO THE PRIOR FRONTIER MEMO
----------------------------------------
The previous write-up called the blocker "the AppStart Monitor per-subsystem SEQUENCING gate —
t106 idles at Ev_receive(want=0x01019007, c=2)".  That is WRONG as a causal statement.

`Ev_receive(0x01019007, c=2, timeout=inf)` on task t106 is NOT a gate.  It is the ordinary idle
wait of AppStartMaster's FThread message dispatcher: the OR of its armed waitable bits, entered
whenever its queues are empty.  The bar8 trace shows t106 entering and leaving that exact wait
dozens of times during a normal boot, e.g.

    [hst] EV< t106 WAIT want=01019007 c=2 to=inf (have=00000000)
    [hst] QS [308]"AppStartMaster" size=52 tag=40c803e0 sndr=t10e notify=01000000->t106
    [hst] EV> t10e -> t106 bits=01000000 (tgt-wait=01019007)
    [hst] EV< t106 want=01019007 c=2 -> caught 01000000 (woke)

t106 sitting in it forever means only "nobody sent AppStartMaster another message".  The real
question is who was supposed to send one — answered below.

Consequently the pinned question "why does a 1-process Server subsystem not satisfy want=0x01019007
c=2 when bar3's winmgr/skmgr/prom/Event/Ed subsystems do?" is malformed: no subsystem ever
"satisfies" that mask.  There is also no 6-subsystem limit, and nothing Server-specific in AppStart.


1. THE ACTUAL SEQUENCING RULE
-----------------------------
The batch (-f=SYS:\batch\<script>) is NOT dispatched all at once.  AppStart::Procedures feeds the
chain ONE script message at a time, and the pump is driven by process-state reports:

  AppStart::Procedures::OnMessage(FmAppStartAction&)            @0x4b420
      action == 0  ->  AppStart::Procedures::DispatchMessageFromProcedure(this)   @0x48c90
                       = read + dispatch the NEXT message from the start script.

  AppStart::Monitor::OnMessage(FmProcessState&)                 @0x3c400
      ps.state == 2 && subsystem.action == 0 && pendingProcesses == 1
          -> FmSubsystemAction(1)                       (subsystem: CREATED  -> INITIALIZING)
      ps.state == 3 && subsystem.action == 1 && pendingProcesses == 1
          -> FmSubsystemAction(2)  AND  FmAppStartAction(0)   <-- THE PUMP
      ps.state == 4 && subsystem.action == 3 && pendingProcesses == 1
          -> FmSubsystemAction(4)

  AppStart::Subsystems::OnMessage(FmLoadSubsystem&)             @0x606b0
      sets subsystem.action (offset +28) and pendingProcesses (offset +32) = number of
      FmLoadProcess entries, and inserts one FmLoadProcess per process into the chain.
      Process names are rewritten to "<subsystem>:<processName>" (e.g. "Server:~/hwserver").

  AppStart::Subsystems::OnMessage(FmProcessState&)              @0x5fed0
      state 2 -> Impl::DecrementPendingProcessesIf(0, idx)
      state 3 -> Impl::DecrementPendingProcessesIf(1, idx)
      state 4 -> Impl::DecrementPendingProcessesIf(3, idx)
      state 5/6 -> DecrementPendingProcesses + EraseProcess
      (Impl::DecrementPendingProcesses @0x5ea00 just decrements Subsystem+32; the
       ...If variant @0x5efb0 logs "Will not decrement number of pending processes,
       subsystem <name> is in other action" when the action does not match.)

So, in one sentence:

  ** The next FmLoadSubsystem in the batch is dispatched only after EVERY process of the
     current subsystem has reported FmProcessState(state = 3, INITIALIZED). **

Client side (libbackend.so), the reporter is:

  FProcess::SynchronizeTransition(FObjectName const&, FStartable::States, ...)   @0x25880
      FSemaphore::Open(<subsystem semaphore>)          ; bail out silently if this fails
      FmProcessState msg;
          msg+4  = (state==2) ? 3 : (state==4) ? 4 : (state==1)+1
          msg+8  = p_ident(0)
          msg+12 = t_ident(0)
          msg+16 = process name (max 32 bytes)
      FMailslotQueue::Write(<AppStartMaster>, msg)
      loop { FSemaphore::RequestWithTimeout(sem, 1, 100000) } until granted
          ; i.e. the child then BLOCKS on the per-subsystem semaphore until
          ; AppStart::Semaphores releases it (ReleaseSemaphoresAfterCreation /
          ; ...AfterInitialization, hwserver-independent; the emulator's
          ; HEROSCALL_SEM_INIT=1 auto-count makes this grant immediately).

On the wire the message is tag 0x40c803e0, 52 bytes, sent to the "AppStartMaster" queue
(id 0x308 in the bar8 run).  Queue registrations to the same queue use tag 0x40c80280.


2. RUNTIME PROOF (bar8, un-fakeable)
------------------------------------
Count of FmProcessState (tag 40c803e0) messages to AppStartMaster, by sender process:

    2  AppStart:AppStart
    2  winmgr:winmgr/winmgr
    2  SkManager:SkManager/skmgr
    2  prom:prom/prom
    2  Event:Event/evtserver
    2  Ed:Ed/mmi
    1  Server:Server/hwserver     <-- ONE.  Never reaches INITIALIZED.

Every healthy process reports twice (CREATED then INITIALIZED).  hwserver reports once.
Therefore Monitor never emits FmAppStartAction(0) for the Server subsystem, Procedures never
dispatches the next script message, and the Nc subsystem is never loaded.  t106's forever-wait
is the symptom, not the cause.

This also re-explains bar6 (bar5 + a separate Nc subsystem): there the 6th subsystem NcS
(startup.elf + ChannelManager) is the one that never reported INITIALIZED.  Nothing to do with
subsystem count or ordering.


3. WHY hwserver NEVER REACHES INITIALIZED
-----------------------------------------
hwserver writes its own log to SYS:\runtime\_HWSERVER.TXT.  From the bar8 run:

    |TRNS|HWSMain|State Init entered.
    |ACTN|HWSMain|Start server interface.
    |ACTN|HWSMain|Start IOC server.
    |TRNS|HWSMain|State SyncBreakpointMain entered.
    |TRNS|HWSMain|State DetectMainboard entered.
    |ACTN|DetectMainboard|detection procedure started.
    |ERRO|DetectMainboard|Could not access configuration data.
    |ERRO|HWSMain|Mainboard detection procedure reported error.
    |ACTN|PlInitThread|Initialize internal PL.
    |ACTN|PlInitThread|Initialization complete.
    |TRNS|HWSMain|State RunUpFailed entered.        <-- terminal

RunUpFailed => the process never completes FStartable initialization => no second
SynchronizeTransition => no FmProcessState(3).

The failing call is the FIRST statement of DetectMainboard::procedure @0x14fb00 (hwserver.elf):

    HWSsmtInitMode mode(-1);
    if ( !HwsMailslot::GetDataSys("initMode", "(value)", srvValue) )   ; 0x14fca2
    {                                                                  ; jz 0x14FE20
        FVerbosePrint(..., LogType 2 /*ERRO*/, "Could not access configuration data.");  // 36 chars
        result.error = 1; AcknowledgeTerminate(); return;
    }
    HwsSrvValue::GetGeneric(mode, 0);
    if ( mode == 2 )                                                   ; 0x14fcc1
    {                                                                  ; jz 0x150EF8
        FVerbosePrint(..., LogType 0, "Hardware simulation mode requested by configuration."); // 52
        -> HWSProgrammingStation  -> detection SUCCEEDS
    }
    ... FSystemPathname marker check -> HWSProgrammingStation (success)
    ... if ( !SearchForPCIDevice(...) ) -> HWSProgrammingStation (success)

NOTE the shape: THREE of the branches end in HWSProgrammingStation and succeed — including the
"no mainboard PCI device found" fallback, which is the natural PGM-Platz outcome.  The ONLY
non-recoverable exit is the very first one: GetDataSys returning false.

Strings resolved from the GOT-relative operands (GOT = 0x575ff4):
    0x433df0  "Could not access configuration data."                  (36)
    0x433db8  "Hardware simulation mode requested by configuration."  (52)
    0x427e09  "initMode"     0x427e01 "(value)"

libhwsinterface.so, the client stack under GetDataSys:
    HwsMailslot::GetDataSys(char const*, char const*, HWS_SRV_VALUE&)   @0xcc20
      -> HwsMailslot::GetDataSys(astring const&, astring const&, ...)   @0xcb30
           ticket = HEUTicketFromStore(2)                               ; 0xcb41
      -> HwsMailslot::GetData(ticket, item, field, out)                 @0xcaa0
           HwsMailslotQueue::Create(0, "GetData", ticket)  ; fails -> return false
           HwsMailslotQueue::GetData(item, field, out)     ; fails -> return false

In the bar8 trace both steps DID complete on the wire — hwserver's own server thread t112
answered its DetectMainboard thread t115:

    QC  "HwsM00000115N000" id=347 owner=t115
    QS  [30c]"QHWServer" tag=008400c0 sndr=t115   ...Server/hwserver:GetData      (create)
    QS  [347] tag=00840100 sndr=t112 size=20                                      (create reply)
    QS  [30c]"QHWServer" tag=00840240 sndr=t115   ...initMode........(value)      (read)
    QS  [347] tag=008404c1 sndr=t112 size=72                                      (read reply)
    QS  [30c]"QHWServer" tag=008400e0 sndr=t115                                   (close)
    QS  [343]"QHWServer_int" tag=40830920 sndr=t115  ...DetectMainboard...|ERRO   (the log line)

so the failure is a NEGATIVE REPLY from hwserver's own server interface, not a lost message and
not an emulator misroute.  (Contrast PlInitThread/t116, which read "mainboard\ident\type" the same
way and succeeded.)

Why the negative reply: "initMode" is the exposed state of a SECOND state machine,
StateMachine<HWSMain, HWSsmtInitMode, HWSMain, HWSDummy>, mapped into the server interface by
HWSMain::EnterInit @0x1d6480 ("Could not map init mode to server interface." is its failure
message, and it did NOT appear, so the mapping succeeded).  But _HWSERVER.TXT contains TRNS lines
only for HWSMain and FwUpdIndicator — there is NO TRNS line for the init-mode state machine, i.e.
it never entered a state, so its exposed value is still the HWSsmtInitMode(-1) "invalid" default
and the read of "(value)" is refused.  _HWSTREE.TXT's `initMode:=FullOperation` is the GEnum's
default rendering, not a set value.

Its transition callback is:

  HWSMain::CheckInitMode(HWSDummy*)   @0x1d5de0
      if ( HWSMain+0x235 != 0 )            -> other path (0x1D6228)
      if ( byte[0x578AAE] == 0 )           -> 0x1D61E7
      SimMode  m = <global SimMode @0x578AC0, value at 0x578AC8>
      CfgSystemInfo cfg;
      if ( m.value == 0 && HWSMain::ReadConfig(cfg) )  m.value = cfg+48;
      map: 0->0, 1->1, 2|3->3, 4->2                       <-- 4 gives the value DetectMainboard wants

  HWSMain::ReadConfig(GMessage&)      @0x1cb130
      linear search of a local std::list `config`; returns FALSE when the list is EMPTY.
      The list is filled ONLY by HWSMain::ReadConfigFile, called from EnterInit under
      `if (configFileGiven)` — i.e. only when hwserver is given -f=<file>.  The genuine batch
      (work/control/sysroot/batch/TNC640heros.txt:89) passes only "-U", so configFileGiven == 0,
      ReadConfig returns false, and m.value stays whatever the command line set.

4g. ★ CORRECTION + THE ACTUAL CHAIN: the request is HWSSrvInspect, not HWSSrvReadConfig
---------------------------------------------------------------------------------------
Section 4f attributed the failure to HWSServer_::HWSServer::ReadConfig.  THAT IS WRONG, and the bar12
result is what exposed it (config fully loaded, failure unchanged).  Disassembling the client-side
request builder settles it — HwsMailslotQueue::GetData(astring,astring,HWS_SRV_VALUE&)@libhwsinterface
+0x21670 constructs an **HWSSrvInspect**, not an HWSSrvReadConfig:

    HWSSrvInspect req; HWSSrvReply reply;
    req->+0x24 = item;      // "initMode"
    req->+0x34 = field;     // "(value)"
    req->+0x0C = this->handle;
    req->+0x18 = 0;
    ... transfer ...
    if (transferOk && reply->+56 == 0) *out = reply->+88;

which also matches the observed 51-byte wire exactly (tag, handle, handle, "initMode", "(value)" —
4+8+8+16+15 = 51, no container).  ReadConfig/"No config data found"/"No primary data" belong to a
DIFFERENT request type and were never on this path.

NCK_SRV_RESULT literal order is now pinned by two independent uses:

4i. ★★★ THE NAMED ROOT CAUSE — user right 27 = NC.DataAccessServiceRead is DENIED
---------------------------------------------------------------------------------
Predicted, then measured, then named. Three independent steps:

(A) PREDICTION from the reply bytes.  Inspect's error reply is emitted from its .cold block, which is
    an EXCEPTION HANDLER (disassembly at 0x80560..0x8063f):

4j. ★★★ CONFIRMED BY FIX — the rights denial IS the cause, and it is now CROSSED
--------------------------------------------------------------------------------
Where the denial comes from (libheuseradmin.so, work/target/rootfs/usr/lib):

  getShm() -> sub_33A0@0x33a0:
      if (shm already resolved) return;
      if ( access("/tmp/__use_network_useradmin", 0) == 0 ) { shm = -2; }        // STATIC path
      else { fd = shm_open("/_heusrv_shm", 0, 0); ... shm = mmap(...); }          // DYNAMIC path

  HEUTestRights(lo, hi, name)@0x8060:
      if (shm == 0 || getTicketData(lo,hi) == 0)   -> return -1
      if (shm != -2)  // DYNAMIC: match `name` against a 64-entry table inside the segment
                      // (tables at shm+0x2000 for "NC.", +8448 "PLC.", +8704 "HEROS.")
                      // not found -> errno=2, return -1
      else            // STATIC: getOptionNameIndex(name) against the ticket's own option bits

  JhUserRights::Test() is `HEUTestRights(...) == 1`, so -1 means DENY.

In this harness heuserver creates /_heusrv_shm but never populates that name table, so the DYNAMIC
path denies everything. Creating the marker file to select the STATIC path was TESTED and changes
nothing (getTicketData does not find our ticket in the local list) — so the marker alone is not the
fix, though it is now created by run_appstart_fex.sh since it is the library's own documented switch.

FIX: emulator/heurights.c — a small LD_PRELOAD shim (knob HEU_GRANT=1, default OFF, wired into
run_appstart_fex.sh exactly like cxathrow/fredfree) that answers HEUTestRights = 1 = granted. This is
emulation of an absent HOST service, in the same class as arena_stub / the heroscalls / /dev/events:
libheuseradmin.so is a HeROS OS library whose backing state is heuserver's user database, which this
project does not reproduce, and the shipped free PGM-Platz runs with full local rights.

NEW FRONTIER (downstream, fresh): hwserver then takes SIGSEGV —
    libheros_sigfaterr: Thread Server/hwserver.Server/hwserver received terminating signal 11
immediately after "HW-Type: NONE - simulated", i.e. inside DetectSik / SikModule on the
just-created ProgrammingStation object. So hwserver still does not reach INITIALIZED and Nc is still
not dispatched — but the blocker is now a crash in newly-reached code, not a rights refusal.
The fault dump (HEROSCALL_BTRACE, already on) identifies it as a
THREAD STACK OVERFLOW, not a bad pointer:

    === [rtos] FAULT sig=0x0000000b eip=0xffce6418 addr=0xd79ffffc
     regs: ... ebp=0x00000004 esp=0xd7a00000
    (and just before: sig=0x0000000b eip=0xffce6956 addr=0x00010021)
    libheros_sigfaterr: Thread Server/hwserver.Server/hwserver received terminating signal 11

  - esp = 0xd7a00000 is exactly PAGE-ALIGNED and the faulting address 0xd79ffffc is esp-4, i.e. the
    first word BELOW the stack's lowest page — the classic guard-page signature.
  - both faulting EIPs fall inside the emulator's own mapping:
        ffce5000-ffce6000 r--p  /var/tmp/lr/lib/heros_rtos.so
        ffce6000-ffcf7000 r-xp  /var/tmp/lr/lib/heros_rtos.so
    so 0xffce6418 = heros_rtos.so +0x1418 and 0xffce6956 = +0x1956.

heros_rtos.so is an i386 LD_PRELOAD and therefore runs on the GUEST thread's stack (see the note at
heros_rtos.c:414). The guest sizes its own thread stacks — the strace shows hwserver's threads created
with clone3 stack_size=0x2dfc0 (188 KB) — and the emulator's frames are charged to that same budget.
heros_rtos has several 16 KB-class stack objects (QMSGCAP / EVTMSGCAP = 16384), so a few nested calls
on a 188 KB guest stack can exhaust it. hwserver only reaches this path now that DetectMainboard
succeeds, which is why it never showed up before.

=> NEW FRONTIER, well scoped: the emulator overflows the guest's own 188 KB thread stack on the
   ProgrammingStation/SikModule path. Fix direction is to stop spending guest stack in heros_rtos —
   move the large per-call buffers (qmsg/evt-sized locals) off the stack (static/TLS or heap) rather
   than to enlarge the guest's stack, which is the guest's choice and not ours to change faithfully.
